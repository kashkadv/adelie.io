# Обговорення: обсяг MVP і стек

- **Статус:** обговорення (рішень ще немає)
- **Створено:** 2026-11-05

Документ для обговорення перед прийняттям рішень. Коли домовимось — рішення
переносяться в ADR (`decisions/`), а план MVP — в окремий файл у `plans/`.

## 1. Спостереження щодо ТЗ

- MVP у ТЗ (розділ 3.1) фактично охоплює етапи 0–5: auth, workspaces + ролі +
  інвайти, 3 платформи, sync-інфраструктура, dashboard, порівняння, AI, звіти.
  Для однієї людини це кілька місяців до першого результату — ризик застрягти.
- **Головний зовнішній ризик — доступ до API платформ**, а не код.
  App review / production access у Meta, TikTok і Pinterest може тривати тижні.
  Тому перевірку API (етап 0) варто почати якомога раніше й паралельно з кодом.
- Для розробки зазвичай достатньо dev/sandbox-режимів із власними акаунтами
  (потребує перевірки на етапі 0, не припущення):
  - Instagram — dev mode застосунку Meta з власними professional-акаунтами;
  - TikTok — sandbox, обмежений набір метрик у Display API;
  - Pinterest — trial access для власного акаунта.

## 2. Пропозиція: «тонкий зріз» MVP

Ідея: якомога швидше пройти весь шлях **підключив акаунт → дані синхронізуються
→ бачу графіки з історією**, на одній платформі. Решта нарощується поверх.

### MVP-1 (перший робочий зріз)

- Реєстрація/логін.
- Один workspace на користувача (створюється автоматично), але модель даних
  одразу multi-tenant (`workspaceId` всюди, перевірка доступу на сервері).
- Одна платформа (кандидат — Instagram, див. питання нижче).
- OAuth-підключення, кілька акаунтів цієї платформи.
- Фонова синхронізація: профіль, публікації, метрики + щоденні snapshots.
- Сторінка акаунта: основні метрики, динаміка, список публікацій із сортуванням.
- Статус синхронізації та ручний перезапуск.

### Відкладається на наступні ітерації

- Інвайти та ролі (Owner/Admin/Analyst/Viewer) — схема готова, UI пізніше.
- Друга і третя платформи.
- Dashboard workspace і порівняння акаунтів/платформ.
- AI-підсумки, звіти.
- Налаштування валюти тощо.

## 3. Стек — варіанти

ТЗ рекомендує: NestJS + Prisma + PostgreSQL + Redis/BullMQ (backend),
Next.js + Tailwind + shadcn/ui (frontend), Docker Compose локально.

**Варіант A — як у ТЗ.** pnpm-монорепо:
`apps/web` (Next.js), `apps/api` (NestJS, REST), `apps/worker` (BullMQ),
`packages/db` (Prisma), `packages/shared` (типи, контракти).
Плюси: чіткий поділ, API-first, легко масштабувати. Мінуси: більше обв'язки на старті.

**Варіант B — спрощений.** Next.js full-stack (route handlers / server actions)
+ окремий worker-процес + спільні пакети `db`/`shared`.
Плюси: швидший старт, менше коду. Мінуси: API не окремий, пізніше може
знадобитись виносити; розходиться з принципом API-first із ТЗ.

Попередня рекомендація: **A**, але без надмірностей на старті (API і worker
можуть бути одним NestJS-проєктом з двома entrypoints).

## 5. Відповіді та прогрес (2026-11-05)

- **Стек:** варіант A → [ADR-0002](../decisions/0002-stack-and-monorepo.md) (прийнято).
- **Auth:** готове безкоштовне рішення без ліцензійних проблем →
  Better Auth, [ADR-0003](../decisions/0003-auth.md) (прийнято).
- **Тестові акаунти:** TikTok і Pinterest є. Instagram — робочий акаунт,
  можливий лише доступ на читання.
- **Перший користувач:** знайомий бізнес Gushka.

### Нотатки

- Instagram read-only: при OAuth ми самі обираємо scopes і можемо запитувати
  лише read-доступ (профіль, медіа, insights) — без публікації чи керування.
  Для dev-режиму акаунт, імовірно, треба додати як тестера застосунку Meta.
  Перевірити на етапі 0.
- Вибір першої платформи залежить від того, де присутній Gushka.
- Gushka — зовнішній користувач, тому для нього знадобиться розгорнуте
  середовище (не лише локальне) і, ймовірно, privacy policy для app review.

### Нові питання

9. Як Gushka користуватиметься: сам заходить в Adelie, чи ти показуєш йому
   результати? (впливає на потребу в інвайтах/ролях у MVP-1)
10. Які акаунти TikTok і Pinterest для тестів — особисті чи бізнесові?

## 6. Відповіді (2026-11-05, частина 2)

- **Gushka присутній на:** Instagram, Pinterest, Etsy. TikTok у Gushka немає.
- **Хто користується:** CEO Gushka (дружина власника проєкту), але всі доступи
  до акаунтів є в нас → для MVP-1 інвайти/ролі не критичні.
- **Тестові акаунти:** TikTok — тестовий, Pinterest — продовий (Gushka).

### Пропозиція порядку платформ (чекає підтвердження)

1. **Pinterest** — перша. Є продовий акаунт Gushka, є доступ, низький ризик
   (на відміну від робочого Instagram). API v5 має аналітику акаунта й пінів.
2. **Instagram** — друга, read-only scopes, після того як пайплайн обкатаний.
3. **TikTok** — пізніше: у Gushka його немає, лише тестовий акаунт.
4. **Etsy** — новий кандидат, у ТЗ не було. Це e-commerce (магазин, товари,
   продажі) → напрям «E-commerce Intelligence» (ТЗ 14.4), поза першим MVP.
   Але для Gushka, ймовірно, саме тут гроші → варто тримати в полі зору.

### Інвайти/ролі

Пропозиція: MVP-1 без UI інвайтів. CEO отримує доступ у MVP-2 через інвайт
(або тимчасово окремий логін в тому ж workspace).

### Auth — питання масштабування

Better Auth self-hosted: немає плати за користувачів, масштабується разом із
нашим PostgreSQL. Ризик — якщо бібліотеку перестануть підтримувати; але код MIT,
дані в нашій БД, тож міграція можлива (ціна — час розробки, не гроші).
Enterprise SSO/SAML — є плагін. Для порівняння: Clerk дорожчає саме з ростом.
