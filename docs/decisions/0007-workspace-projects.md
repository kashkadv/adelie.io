# ADR-0007: Структура простору — workspace → проєкти → акаунти

- **Статус:** прийнято
- **Дата:** 2026-11-05
- **Змінює:** ТЗ §4.1–4.2 (там workspace = і команда, і акаунти)

## Контекст

Ключовий користувач — SMM-агенція з багатьма клієнтами; у клієнта кілька акаунтів на різних
платформах; співробітники агенції ведуть не всіх клієнтів. Також Adelie використовують бізнеси
без агенції (Gushka). У моделі ТЗ, де кожен клієнт — окремий workspace, агенція не має спільної
команди й загального огляду, а співробітників треба додавати в кожен workspace окремо.

## Рішення

```text
Workspace (організація: агенція або бізнес)   ← межа ізоляції даних, команда, ролі, оплата
 └── Project (проєкт: клієнт агенції або бренд) ← акаунти, налаштування, звіти, доступи
      └── SocialAccount (Pinterest, Instagram…)
```

- **Назва рівня — «Проєкт» / «Project»** для всіх типів простору (обрано власником продукту як
  найприроднішу). У коді та БД — `Project`.
- **Workspace** — tenant: усі дані мають `workspaceId`, ізоляція між workspace як і раніше (ТЗ §4.3).
- **Project** — налаштування клієнта/бренду: часовий пояс, валюта, мова звітів.
- **Ролі в workspace:** Owner, Admin — бачать усі проєкти; Manager, Analyst, Viewer — лише
  **призначені їм** проєкти (призначення на рівні проєкту з першої версії).
  - Manager: підключає акаунти, робить звіти; Analyst: перегляд і звіти; Viewer: лише перегляд.
- **Клієнти агенції в Adelie не входять.** Замість кабінету для клієнта — **звіти, якими можна
  поділитися**: «заморожений» знімок за період, доступний за секретним посиланням (з відкликанням
  і строком дії); згодом — PDF.
- **Підключення акаунта клієнтом за запрошенням** (агенція надсилає посилання, клієнт сам дає OAuth-доступ)
  — модель даних це враховує; реалізація пізніше (у MVP-1 акаунти Gushka підключає власник).

## Альтернативи

- **Workspace на кожного клієнта** (як у ТЗ) — простіше на старті, але без спільної команди,
  загального огляду агенції та з дублюванням доступів.
- **Назви «Клієнт» / «Бренд»** — кожна природна лише для одного типу користувачів;
  варіант із різними підписами для агенцій і брендів відкинуто на користь однієї назви.
- **Гостьові входи для клієнтів** — відкладено: звіти за посиланням покривають потребу простіше.

## Наслідки

- Нова сутність `Project`; `SocialConnection`/`SocialAccount`/метрики/звіти прив'язуються до проєкту
  (плюс `workspaceId` для ізоляції).
- Перевірка доступу двоступенева: членство у workspace + (для Manager/Analyst/Viewer) призначення на проєкт.
- Загальний огляд workspace (по всіх проєктах) — частина продукту, не лише огляд одного акаунта.
- Під час реєстрації створюється workspace і перший проєкт.
