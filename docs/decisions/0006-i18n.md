# ADR-0006: Мультимовність інтерфейсу

- **Статус:** прийнято
- **Дата:** 2026-11-05

## Контекст

На старті інтерфейс потрібен англійською та українською, а додати нову мову
має бути можна на будь-якому етапі без переробок.

## Рішення

- Бібліотека **next-intl** у `apps/web`, режим **без мовних префіксів в URL**
  (застосунок за логіном, SEO не потрібне). Для майбутнього публічного лендінгу
  можна буде додати префікси (`/en`, `/uk`) окремо.
- Визначення мови: cookie `locale` (явний вибір користувача) → заголовок
  `Accept-Language` браузера → `en`. Пізніше — збережене налаштування користувача в БД.
- Тексти — у `apps/web/messages/<locale>.json`. **Англійська — джерело правди:**
  типи згенеровано з `en.json`, використання неіснуючого ключа — помилка TypeScript.
- `pnpm --filter @adelie/web lint` перевіряє, що всі мовні файли мають ті самі ключі, що й `en.json`.
- Перемикач мови в інтерфейсі (`LocaleSwitcher`).

### Як додати мову

1. Додати код у `locales` і назву в `localeLabels` — `apps/web/src/i18n/config.ts`.
2. Створити `apps/web/messages/<код>.json` (скопіювати `en.json` і перекласти).
3. `pnpm --filter @adelie/web lint` — переконатись, що ключі збігаються.

## Альтернативи

- Мовні префікси в URL (`/uk/...`) — зайва складність для застосунку за логіном.
- Власне рішення на React context — немає типізації, форматування дат/чисел, плюралізації.

## Наслідки

- Жодних «зашитих» текстів у компонентах — тільки через `useTranslations` / `getTranslations`.
- Кожна зміна UI-текстів оновлює **всі** мовні файли в тому ж коміті.
- Повідомлення про помилки від Better Auth поки англійською — локалізуємо пізніше
  (за кодами помилок).
- Next 16 `cacheComponents`: читання мови (cookies) відбувається всередині `<Suspense>`
  у кореневому layout; `<html lang>` оновлюється на клієнті.
