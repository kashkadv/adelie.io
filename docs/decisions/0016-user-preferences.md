# ADR-0016: Налаштування інтерфейсу користувача

- **Статус:** прийнято
- **Дата:** 2026-11-07

## Контекст

Різним людям потрібні різні дані: у таблиці «Контенту» хтось дивиться на покази й переходи, хтось — на
охоплення й лайки. Потрібно, щоб кожен міг обрати колонки та їхній порядок, окремо для кожної платформи, і щоб
вибір був однаковим на всіх пристроях. Згодом таких налаштувань стане більше (вигляд «Огляду», сповіщення тощо).

## Рішення

- Таблиця `user_preference` (`userId`, `key`, `value` JSON) — загальне сховище налаштувань інтерфейсу користувача.
  Відсутній ключ = стандартне значення продукту.
- API: `GET /me/preferences` (усі одразу), `PUT /me/preferences/:key`, `DELETE /me/preferences/:key` (скинути).
  Кожен ключ відомий API, значення валідуються (`apps/api/src/preferences/preferences.ts`) — довільні дані не
  зберігаються.
- Перший ключ — `content.columns.<PLATFORM>`: `{ columns: [...] }`, показані колонки в їхньому порядку.
- Налаштування **на користувача, спільні для всіх проєктів** (людина зазвичай дивиться на ті самі метрики).
- Застосунок змінює вигляд одразу, зберігає з невеликою затримкою (перетягування дає один запит).
- CSV з «Контенту» вивантажує показані колонки в їхньому порядку; галочка «Усі метрики» — усі метрики платформи.

## Альтернативи

- `localStorage` — не переходить між пристроями й браузерами.
- Окремі колонки в `user_profile` на кожне налаштування — міграція на кожну дрібницю інтерфейсу.
- Налаштування на проєкт — відкладено: поки немає запиту; ключ можна розширити (`…:<projectId>`).

## Наслідки

- Нові налаштування додаються без міграцій: ключ + валідатор.
- Список колонок платформи дубльовано у web і API (`ALL_COLUMNS` / `CONTENT_COLUMNS`); змінюючи — оновлювати обидва.
  Збережений вибір із колонками, яких уже немає, тихо очищується на клієнті.
