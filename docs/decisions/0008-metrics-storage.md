# ADR-0008: Зберігання метрик соцмереж

- **Статус:** прийнято
- **Дата:** 2026-11-05
- **Деталі моделі:** [plans/stage-2-data-model.md](../plans/stage-2-data-model.md)

## Контекст

Adelie збирає метрики з кількох платформ (першою — Pinterest). Кожна платформа має свій набір метрик,
статуси даних (READY / PROCESSING / ESTIMATE…) і обмежену глибину історії (Pinterest — 90 днів).
ТЗ вимагає: «немає даних ≠ 0», не сумувати несумовне, зберігати походження значення, ідемпотентну
синхронізацію. Втрачені дані старші 90 днів у платформи вже не перезапитати.

## Рішення

1. **«Довгий» формат метрик** — джерело правди: рядок = (об'єкт, метрика, дата, розрізи) → значення
   або `null`, статус даних, походження. Нові метрики й платформи — без міграцій; правила агрегації —
   у довіднику `MetricDefinition`. Фізично — **дві таблиці** однакової форми (уточнено під час реалізації
   схеми, 2026-11-05): `AccountMetricValue` (денний ряд акаунта, зберігається завжди) і `PostMetricValue`
   (знімки піна, пишуться лише при зміні). У них різна семантика дати й різні правила зберігання;
   до того ж унікальний ключ з порожнім `postId` у Postgres не працює (NULL ≠ NULL).
2. **Похідний шар для читання:** таблиця `PostMetricsLatest` («широкий» рядок на пін) перераховується
   задачею worker'а після синхронізації акаунта. Проєкт / тиждень / місяць — рахуємо запитом з денних
   даних, не зберігаємо.
3. **Обсяг:** дані акаунта × день зберігаються завжди; знімки метрик пінів пишуться лише при зміні значення;
   прорідження старих знімків пінів (тиждень → місяць) — пізніше, нічною задачею.
4. **Сирі відповіді API** (`SyncPayload`, `jsonb`) зберігаються 90 днів — щоб перерахувати метрики при
   помилці маппінгу і для дебагу. Без заголовків запиту (токенів там немає).
5. **Дошки Pinterest** — легка таблиця `SocialBoard`; аналітика дошок — наша агрегація метрик пінів.
6. **Час:** дні зберігаємо як віддає платформа (доба UTC), показуємо в часовому поясі проєкту.
7. **Розбивка за пристроями** (`app_type`) — збираємо на рівні акаунта з першого дня (+1 запит), на рівні
   пінів — ні; показ у UI — пізніше.

## Альтернативи

- **Окремі колонки під кожну метрику/платформу** — простіші запити й сортування, але міграція на кожну
  нову метрику, немає статусу й походження на рівні значення. Перевагу «зручно сортувати» покриває
  похідна таблиця.
- **Агрегувати в добові/тижневі/місячні таблиці проєкту і видаляти деталі** — втрачаються розрізи по
  акаунтах і пінах, порівняння несумісних платформ, а видалене не відновити (90 днів історії).
  Денні дані акаунта дешеві; тижні й місяці збираються з них запитом.
- **Не зберігати сирі відповіді** — менше місця, але помилку маппінгу в даних старших 90 днів уже не виправити.

## Наслідки

- Агрегатор мусить враховувати `MetricDefinition.aggregation` (SUM / LAST / перерахунок rate з компонентів),
  статус агрегату — найгірший серед складових, немає даних → `null`.
- Потрібні задачі worker'а: перерахунок `PostMetricsLatest` після синхронізації, очищення `SyncPayload`
  старших 90 днів, згодом — прорідження знімків пінів.
- Видалення акаунта/workspace видаляє і метрики, і сирі відповіді.
- `split_field=APP_TYPE` на `/user_account/analytics` перевірити в PoC 2.
