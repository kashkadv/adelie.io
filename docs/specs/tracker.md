# Adelie Tracker — Website Events & Attribution

- **Документ:** окрема технічна та продуктова специфікація модуля
- **Версія:** 1.0 (від власника продукту, 2026-11-06)
- **Статус:** реалізація розпочата під назвою **Flipper** — перший етап (скрипт, Events API, події магазину, джерела,
  анонімний режим до згоди): [ADR-0022](../decisions/0022-flipper-tracker.md), [guides/flipper.md](../guides/flipper.md)
- **Пріоритет:** закласти архітектурну основу; повний функціонал реалізовувати поетапно.

---

## A.1. Мета

Adelie має надавати власнику сайту універсальний JavaScript-трекер, який встановлюється один раз і передає до платформи події відвідувачів, інформацію про джерела трафіку та конверсії.

Мета — пов'язати маркетингові контакти (Pinterest, Instagram, TikTok, Google, рекламні кампанії, email, referral тощо) з поведінкою на сайті та бізнес-результатами: лідами, замовленнями й доходом.

Базовий принцип:

**Один сайт → один встановлений скрипт → єдиний потік подій для всіх підтримуваних маркетингових каналів.**

Adelie Tracker має бути незалежним від конкретної соціальної мережі. Pinterest — перша інтеграція/сценарій використання, але модель даних повинна бути універсальною.

## A.2. Основні можливості

### A.2.1. Встановлення трекера

Для кожного сайту в Adelie створюється окремий `site_id` та конфігурація відстеження.

Приклад встановлення:

```html
<script
  src="https://cdn.adelie.space/tracker.js"
  data-site-id="SITE_ID"
  async
></script>
```

Вимоги:
- скрипт має бути асинхронним і не блокувати завантаження сайту;
- конфігурація має бути прив'язана до конкретного `site_id`;
- SDK має підтримувати кешування конфігурації та її оновлення;
- події мають передаватися через захищений Events API;
- помилки трекера не повинні ламати роботу сайту;
- передбачити середовища production/staging або allowlist доменів;
- не вважати `site_id` секретом: він ідентифікує сайт, але не є механізмом автентифікації.

### A.2.2. Автоматичні події

Початковий набір:
- `PageView`;
- `PageLeave` або інша обережна метрика завершення перегляду, якщо її реалізація дає надійні дані;
- `OutboundClick`;
- `Scroll` (за потреби та з контрольованою частотою);
- `FormStart` / `FormSubmit` без збору значень полів;
- `ProductView`, якщо товарні дані доступні;
- SPA route change для React, Next.js та інших SPA-сайтів.

Автоматичне відстеження не повинно збирати вміст полів форм, паролі, платіжні дані або іншу чутливу інформацію.

### A.2.3. Налаштовувані події через адмін-панель

Адміністратор сайту має мати змогу налаштовувати події без повторного розгортання скрипта.

Приклад конфігурації:
- назва події: `AddToCart`;
- тип тригера: click;
- CSS selector: `button.add-to-cart`;
- додаткові параметри: лише явно дозволені та безпечні значення;
- статус: active/inactive.

SDK завантажує конфігурацію сайту та застосовує правила на сторінках.

Важливо:
- не виконувати довільний JavaScript, отриманий із конфігурації;
- підтримувати делегування подій, щоб працювати з динамічно створеними елементами;
- обережно працювати з CSS-селекторами та обмежувати їхню складність;
- передбачити тестовий режим і перевірку, чи спрацьовує правило;
- не трактувати клік по кнопці як підтверджену бізнес-конверсію.

### A.2.4. Data attributes

Для надійнішого відстеження розробник сайту може додавати спеціальні атрибути:

```html
<button
  data-adelie-event="AddToCart"
  data-adelie-product-id="product-123"
>
  Add to cart
</button>
```

SDK має вміти виявляти такі атрибути та формувати подію.

### A.2.5. JavaScript API

Для складних сценаріїв передбачити публічний API:

```javascript
window.adelie.track("Purchase", {
  order_id: "ORD-123",
  value: 149.99,
  currency: "EUR"
});
```

Приклади використання:
- підтверджена покупка після успішної відповіді backend;
- успішне створення ліда;
- реєстрація;
- підписка;
- кастомна бізнес-подія.

Для `Purchase` бажано використовувати серверне підтвердження або webhook e-commerce платформи. Клієнтський виклик сам по собі не є достатнім доказом успішної оплати.

### A.2.6. Visual Event Builder

У перспективі реалізувати режим налаштування подій через візуальний вибір елементів:
1. Адміністратор відкриває сайт у режимі налаштування Adelie.
2. Вибирає елемент сторінки.
3. Adelie пропонує CSS-селектор та тип події.
4. Адміністратор задає назву й підтверджує правило.
5. Конфігурація стає доступною трекеру.

Це має бути зручний інтерфейс для маркетолога без необхідності редагувати код сайту. Водночас складні конверсії повинні підтримувати JavaScript API або серверну інтеграцію.

## A.3. Визначення джерела трафіку

Adelie має класифікувати джерело кожного нового сеансу на основі доступних сигналів.

### A.3.1. Пріоритет сигналів

Рекомендований порядок:
1. Валідні UTM-параметри та власні параметри кампаній у landing URL.
2. Відомі рекламні click ID, якщо вони присутні.
3. `document.referrer` та домен referrer.
4. Direct — якщо немає ні campaign-параметрів, ні придатного referrer.
5. Unknown/Other — якщо джерело неможливо надійно визначити.

UTM-параметри є мітками, які додає маркетолог або рекламна платформа. Їх не можна вважати криптографічно підтвердженим джерелом: вони можуть бути відсутніми, зміненими або підробленими.

### A.3.2. Канали

Початковий перелік каналів:
- `Organic Search` — Google, Bing та інші пошукові системи;
- `Paid Search`;
- `Organic Social`;
- `Paid Social`;
- `Referral`;
- `Email`;
- `Affiliate`;
- `Display`;
- `Direct`;
- `Other` / `Unknown`.

Джерело (`source`), тип трафіку (`medium`) і канал (`channel`) потрібно зберігати окремо. Не зводити всі значення до одного поля.

### A.3.3. Referrer

На першому перегляді сторінки SDK може зчитати `document.referrer` і передати:
- referrer URL або нормалізований домен;
- landing page;
- timestamp;
- поточні campaign-параметри.

Обмеження:
- referrer може бути порожнім через політику браузера, налаштування `Referrer-Policy`, застосунок-посередник або приватні режими;
- referrer часто містить лише домен, а не повний шлях;
- referrer не завжди дозволяє визначити конкретну публікацію;
- не можна вважати відсутність referrer доказом прямого введення URL.

### A.3.4. UTM та власні параметри Adelie

Підтримати стандартні параметри:
- `utm_source`;
- `utm_medium`;
- `utm_campaign`;
- `utm_content`;
- `utm_term`.

Додатково можна підтримати внутрішні параметри Adelie, наприклад:
- `ad_campaign_id`;
- `ad_account_id`;
- `social_post_id`;
- `pin_id`;
- `creative_id`;
- `partner_id`.

Внутрішні параметри не повинні дублювати стандартні UTM без потреби. Вони потрібні для точного зіставлення з сутностями Adelie, коли такі ID відомі платформі.

## A.4. Link Builder

У веб-інтерфейсі Adelie реалізувати генератор відстежуваних посилань.

Користувач задає:
- destination URL;
- платформу / source;
- тип трафіку / medium;
- campaign;
- content або ID публікації;
- за потреби додаткові ідентифікатори.

Приклади:

```text
https://shop.example/products/blanket
?utm_source=pinterest
&utm_medium=organic_social
&utm_campaign=winter_collection
&utm_content=pin_123
```

```text
https://shop.example/products/blanket
?utm_source=instagram
&utm_medium=organic_social
&utm_campaign=winter_collection
&utm_content=story_456
```

```text
https://shop.example/products/blanket
?utm_source=tiktok
&utm_medium=organic_social
&utm_campaign=winter_collection
&utm_content=video_789
```

Вимоги:
- коректно додавати параметри до URL, який уже містить query string;
- зберігати наявні параметри destination URL;
- коректно працювати з URL encoding;
- підтримувати копіювання посилання;
- зберігати історію створених посилань;
- за можливості пов'язувати посилання з campaign, post, pin або creative у внутрішній моделі Adelie;
- не припускати, що кожна соціальна платформа дозволяє автоматично змінити URL уже опублікованого матеріалу.

## A.5. Ідентифікація відвідувачів та сесій

Використовувати окремі поняття:
- `visitor_id` — псевдонімний first-party ідентифікатор браузера в межах конкретного сайту;
- `session_id` — ідентифікатор сеансу;
- `touchpoint_id` — конкретний маркетинговий контакт/перехід;
- `click_id` — рекламний ідентифікатор переходу, якщо його передала платформа;
- `user_id` — ідентифікатор авторизованого користувача, лише якщо сайт має законну підставу та явно передає його;
- `order_id` — ідентифікатор замовлення.

Не використовувати прихований browser fingerprinting для обходу обмежень cookies або consent. Не намагатися об'єднувати відвідувачів різних сайтів у спільний профіль без окремої законної підстави та належної прозорості.

Ідентифікатори мають бути scoped до сайту/клієнта. Не допускати випадкового зіставлення visitor ID між різними клієнтами Adelie.

## A.6. Атрибуція

Зберігати touchpoints окремо від подій. Це дозволить застосовувати різні моделі атрибуції без повторного збору даних.

Мінімально підтримати:
- First touch;
- Last non-direct touch;
- Last touch;
- за потреби — лінійні або позиційні моделі в майбутньому.

Приклад:
1. Користувач переходить із Pinterest.
2. Відвідує кілька сторінок.
3. Повертається через кілька днів напряму.
4. Здійснює покупку.

У такому сценарії:
- First touch = Pinterest;
- Last non-direct touch = Pinterest;
- Last touch = Direct.

Модель атрибуції має бути явно показана у звіті. Не називати атрибуцію точною, якщо дані неповні або користувачі не можуть бути надійно зіставлені.

## A.7. Зв'язок із платформами та зовнішніми джерелами

Adelie має об'єднувати кілька різних джерел даних, не змішуючи їхню семантику.

### Adelie Tracker
Надає:
- browser sessions;
- page views;
- поведінкові події;
- події кошика;
- ліди;
- покупки та дохід, якщо вони передані сайтом;
- відомі campaign-параметри та referrer.

### Social platform APIs
Надають платформні метрики:
- покази;
- збереження;
- кліки;
- перегляди;
- взаємодії;
- статистику власних акаунтів у межах дозволів API.

### Google Search Console
Після підключення та надання дозволу клієнтом може надавати агреговані дані:
- пошукові запити;
- покази;
- кліки;
- CTR;
- середню позицію;
- сторінки;
- країни та пристрої.

Важливе обмеження: Search Console не надає персонального зв'язку між конкретним пошуковим запитом і конкретною browser-сесією. Дані Search Console агреговані, а частина запитів може бути прихована з міркувань приватності.

Adelie може зіставляти агреговані SEO-показники зі своїми даними про landing pages та конверсії на рівні сторінок/періодів, але не повинна стверджувати, що знає точний keyword кожного покупця.

## A.8. Єдина модель подій

Рекомендована базова структура події:

```typescript
interface AdelieEvent {
  id: string;
  siteId: string;
  eventName: string;

  visitorId?: string;
  sessionId?: string;
  touchpointId?: string;

  occurredAt: string;
  pageUrl?: string;
  pageTitle?: string;

  properties?: Record<string, string | number | boolean | null>;
}
```

Рекомендована базова структура touchpoint:

```typescript
interface AttributionTouchpoint {
  id: string;
  siteId: string;
  visitorId?: string;
  sessionId?: string;

  source?: string;
  medium?: string;
  campaign?: string;
  content?: string;
  term?: string;
  channel: string;

  referrerDomain?: string;
  landingPage: string;
  clickIdType?: string;
  clickId?: string;

  occurredAt: string;
}
```

Рекомендовані доменні сутності:
- `TrackedSite`;
- `TrackerConfiguration`;
- `TrackedEventRule`;
- `WebsiteEvent`;
- `Visitor`;
- `Session`;
- `AttributionTouchpoint`;
- `Conversion`;
- `TrackedLink`.

Остаточну схему БД слід узгодити з наявною Prisma-моделлю та вимогами до обсягу подій. Для великих обсягів подій може знадобитися окреме аналітичне сховище.

## A.9. Pipeline обробки

Рекомендований потік:

1. SDK збирає дозволені дані та формує подію.
2. SDK надсилає подію до Events API.
3. API перевіряє `site_id`, домен, формат, розмір payload та rate limits.
4. Подія потрапляє в чергу.
5. Worker нормалізує джерело, канал, URL та event properties.
6. Виконується дедуплікація за event ID / idempotency key.
7. Подія записується у сховище.
8. Attribution Engine пов'язує подію з visitor, session та доступним touchpoint.
9. Аналітика формує funnels, conversion rates, revenue та channel reports.

Не покладатися на порядок доставки подій: браузерні події можуть надходити із затримкою або повторно. Зберігати час виникнення події окремо від часу її отримання сервером.

## A.10. Приватність, consent та безпека

Adelie Tracker має бути privacy-aware за замовчуванням.

Вимоги:
- підтримка consent state та інтеграції з consent management platforms;
- не встановлювати необов'язкові ідентифікатори й не збирати необов'язкові дані до отримання необхідної згоди;
- поважати відмову, відкликання згоди та opt-out;
- мінімізувати дані та строки зберігання;
- передбачити видалення/експорт даних відповідно до застосовних вимог;
- не збирати паролі, платіжні реквізити, значення полів форм та інші чутливі дані;
- не передавати повний URL, якщо він може містити персональні або секретні параметри; перед відправленням очищати query parameters за allowlist;
- не використовувати fingerprinting для обходу consent або browser restrictions;
- документувати цілі обробки, категорії даних, одержувачів і строки зберігання;
- враховувати GDPR та ePrivacy requirements для європейських користувачів.

`site_id` не є секретом. Захист Events API має спиратися на allowlist доменів як допоміжний сигнал, rate limiting, валідацію payload, anti-abuse механізми та інші серверні перевірки. Не покладатися лише на `Origin` або `Referer`, оскільки клієнтські запити можна підробити.

## A.11. Обмеження та коректність даних

- `document.referrer` може бути порожнім або неповним.
- UTM-параметри можуть бути відсутніми або некоректними.
- Click ID не є універсальним ідентифікатором людини.
- Кліки рекламної платформи, browser sessions та landing page views — різні метрики й не зобов'язані збігатися.
- Користувач може змінити браузер, пристрій або очистити cookies.
- Блокувальники реклами та браузерні обмеження можуть блокувати SDK.
- Cross-device attribution не гарантується без додаткових законних і достовірних сигналів.
- Органічні пошукові запити зазвичай не доступні в `document.referrer`; для агрегованої SEO-аналітики потрібна інтеграція з Google Search Console або іншим дозволеним джерелом.

У звітах слід показувати рівень повноти/надійності даних та чітко відрізняти виміряні значення від оцінок.

## A.12. Рекомендований порядок реалізації

**Етап 1 — базовий трекер**
- `site_id` та встановлення SDK;
- PageView;
- referrer;
- UTM parsing;
- visitor/session ID з урахуванням consent;
- Events API та збереження подій.

**Етап 2 — Link Builder та канали**
- генератор UTM-посилань;
- нормалізація source/medium/channel;
- збереження Tracked Links;
- звіти за джерелами та landing pages.

**Етап 3 — події й конверсії**
- CSS selector rules;
- data attributes;
- JavaScript API;
- e-commerce events;
- дедуплікація та підтвердження Purchase.

**Етап 4 — атрибуція**
- touchpoint history;
- First touch / Last non-direct / Last touch;
- conversion funnels;
- зв'язок із Pinterest та іншими platform metrics.

**Етап 5 — розширені можливості**
- Visual Event Builder;
- інтеграції Shopify/WooCommerce;
- server-side events та webhooks;
- Google Search Console;
- consent manager integrations;
- розширені моделі атрибуції.

## A.13. Критерії готовності першої версії

- Клієнт може створити сайт у Adelie та отримати код встановлення.
- Встановлений SDK передає PageView без блокування сайту.
- SDK визначає UTM-параметри та доступний referrer.
- Події пов'язуються з visitor/session у межах дозволеної моделі згоди.
- Адміністратор бачить події та джерела трафіку в Adelie.
- Повторне надсилання події не створює дубль конверсії.
- Відмова від необов'язкового tracking припиняє відповідний збір.
- Непідтверджений клік не зараховується як Purchase.
- Дані різних сайтів/клієнтів ізольовані.

## Нотатки (обговорення 2026-11-06)

- **Перший сценарій — Gushka:** має власний сайт (**Next.js + Sanity + NestJS**, повний контроль над кодом), туди можна встановити скрипт. Продажі також на Etsy —
  на сторінки Etsy скрипт поставити неможливо; там допомагають лише UTM-мітки (Link Builder), видимі в статистиці Etsy.
- **Чому не відкладати надовго:** історія подій накопичується лише з моменту встановлення скрипта (як і метрики
  Pinterest) — що раніше він на сайті, то більше даних для звітів.
- **Запропонований порядок:** спершу етап 2 MVP-1 (Pinterest end-to-end) → трекер етап 1 (PageView, referrer, UTM,
  visitor/session з урахуванням згоди, Events API) + Link Builder → далі конверсії й атрибуція.
- **Зв'язок із моделлю даних:** сайт — ще одне джерело в **проєкті** (ADR-0007), поруч із соцакаунтами;
  `utm_content`/`pin_id` зіставляються з `SocialPost.externalId`.
- **Рішення, які треба буде ухвалити (ADR перед реалізацією):**
  - інфраструктура прийому подій — публічний, високонавантажений, критичний до доступності сервіс; домашній
    Proxmox ризикований; сховище — Postgres на старті, окреме аналітичне (напр. ClickHouse) при великих обсягах;
  - режим згоди: cookie з `visitor_id` для ЄС потребує згоди; можливий «режим без згоди» з агрегованою статистикою;
  - блокувальники реклами: скрипт із чужого домену блокують — згодом проксі через домен клієнта;
- **Сайт Gushka (Next.js + Sanity + NestJS) — наслідки для реалізації:**
  - **Purchase — лише з сервера:** після успішної оплати бекенд NestJS надсилає подію в Events API із секретним
    серверним ключем сайту (окремим від публічного `site_id`); дедуплікація за `order_id`. Клієнтський
    `track("Purchase")` не рахується як підтверджена покупка.
  - **SPA:** трекер відстежує зміни маршруту Next.js (History API), а не лише перше завантаження; встановлення —
    через `next/script` у кореневому layout.
  - **Товари:** ID документів Sanity передаються в `ProductView`/`Purchase` — звіти «які товари продає канал».
  - Згодом — npm-пакет для Next.js (компонент + серверний клієнт) для інших клієнтів.
